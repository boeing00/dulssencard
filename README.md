# 덜쎈카드 (DulSsenCard)

결제 통지를 **기기 안에서** 분류해, 사용자가 설정한 카드별 월간 추적 목표와 개인 구매 추적
한도의 진행 상황을 보여 주는 Android 앱.

- 기준 문서: `DulSsenCard_PRD_v4_ImplementationReady.md` (정책·권한은 이 문서를 따른다)
- 디자인: `design_handoff_dulssencard/` 핸드오프 (토큰·화면 스펙·집계 규칙)
- **작업을 이어받는다면 `CLAUDE.md` 를 먼저 읽을 것** — 빌드 방법·함정·다음 할 일이 거기 있다

## 1. PRD 대비 달라진 점

구현하면서 PRD 와 어긋나게 결정한 것들이다. **여기 적힌 것 말고는 PRD 를 따른다.**

### 1.1 수집 소스를 셋으로 확장하고, 권한은 알림 접근 하나로 (사용자 지시)

PRD §4 비목표에는 *"알림 접근 권한을 통한 앱 푸시 파싱"* 이 명시적으로 제외돼 있었다.
실제 한국 카드 결제 통지가 문자에서 카드사 앱 푸시·카카오 알림톡으로 옮겨간 현실에 맞춰
사용자 요청으로 되살렸고, 이어서 **SMS 권한을 완전히 버리는 쪽으로 다시 결정했다.**

| 소스 | 어디서 읽나 | 기본값 |
|---|---|---|
| 결제 SMS | 기본 문자 앱이 띄운 **알림** | 켬 |
| 카드사 앱 푸시 | 카드사 앱 알림 | 켬 |
| 카카오톡 결제 알림톡 | 카카오톡 알림 | **끔** — 아래 1.2 참고 |

**선언하는 민감 권한은 `BIND_NOTIFICATION_LISTENER_SERVICE` 하나뿐이다.**
`RECEIVE_SMS` / `READ_SMS` 를 선언하지 않으므로 Play 의 SMS·통화기록 권한 그룹 심사를
통째로 피한다(§5 참고). 결제 문자 커버리지는 문자 앱 알림으로 유지된다.

파싱·집계·보정 규칙은 소스와 무관하게 동일하다. 거래에 `source` 를 남기고,
문자 앱이 띄운 알림은 `TxSource.SMS` 로 분류해 상세 화면에서 경로를 구분할 수 있게 했다.

**이 구조의 약점**: 사용자가 문자 앱 알림을 꺼 두면 결제 문자를 통째로 놓친다.
홈 상단 배너(`CollectionGap.SMS_APP_OFF`)가 그 상태를 감지해 알려 준다.

### 1.2 알림은 허용 목록 방식

알림 접근은 기기의 **모든** 알림을 볼 수 있는 넓은 권한이다. 그래서
`PaymentNotificationListener` 는 패키지명을 먼저 보고, 사용자가 켜지 않은 앱이면
**본문을 꺼내기 전에** 반환한다. 꺼진 앱에 대해 남기는 것은 "이 앱이 알림을 띄운 적 있다"는
사실(패키지명·앱 이름·시각)뿐이다.

첫 실행 때 설치된 카드사 앱과 **기본 문자 앱**을 목록에 미리 채우고 **켜 둔다**
(문자 앱을 꺼 두면 결제 문자를 읽을 통로가 없다). 카카오톡은 목록에 넣되 **꺼 둔다** —
카드사 앱 알림은 결제 통지가 전부지만 카카오톡은 일상 대화가 오가는 메신저라, 사용자가
명시적으로 켜게 했다. (`DulSsenRepository.seedKnownSourceApps`)

어느 쪽이든 결제 통지가 아닌 알림은 파서가 즉시 버리고 아무것도 저장하지 않는다.

### 1.3 지문(fingerprint) 정의 변경 — **가장 중요한 변경**

PRD §8 은 지문을 *"발신 식별자·정규화 시각·금액·상태를 일방향 해시한 값"* 으로 정의했다.
소스가 SMS 하나일 때는 맞았지만, 지금은 **같은 결제 한 건이 문자로도 오고 푸시로도 온다.**
발신 식별자(전화번호 vs 패키지명)를 지문에 넣으면 지문이 갈라져 **한 번 쓴 돈이 두 번 집계된다.**

그래서 지문에서 전송 경로와 표기 차이를 걷어냈다:

```
지문 = SHA-256( 카드사 | 분 단위 거래 시각 | 금액 | 승인/취소 )
```

- **뺀 것**: 발신 식별자, 카드 뒷4자리, 가맹점명.
  문자에는 `(1234)` 가 있는데 푸시에는 없고, 가맹점도 `이마트 성수` / `이마트성수점` 처럼
  경로마다 표기가 다르다. 넣으면 같은 결제가 다른 지문을 갖는다.
- **남는 위험**: 같은 카드사에서 같은 분에 같은 금액을 두 번 긁으면 지문이 겹친다.
  조용히 버리면 결제를 잃으므로, `Ingestor` 가 가맹점 표기와 수신 시각을 함께 보고
  판단이 서지 않으면 `DUPLICATE_SUSPECTED`(확인 필요)로 남겨 사용자에게 넘긴다.

판정 규칙 (`Ingestor.ingest`):

| 상황 | 처리 |
|---|---|
| 지문 일치 + 가맹점 충돌 없음 + 수신 15분 이내 | **중복 — 버린다** (문자+푸시 정상 동작) |
| 지문 일치 + 가맹점이 명백히 다른 가게 | 별개 결제로 넣되 `확인 필요` |
| 지문 일치 + 수신 시각이 멀리 떨어짐 | 별개 결제로 넣되 `확인 필요` |

DB 의 `messageFingerprint` 유니크 인덱스 + `INSERT OR IGNORE` 가 마지막 방어선이다
(두 소스가 동시에 들어와 경합해도 한 건만 남는다).

### 1.4 광고

PRD §4 는 광고를 비목표로 두었고, 디자인 핸드오프에는 홈에 320×50 배너 지면이 있었다.
**자리와 코드만 넣고 꺼 두는 것**으로 결정했다.

- `BuildConfig.ADS_ENABLED = false` — `AdSlot` 이 아예 그려지지 않는다.
- **광고 SDK 는 의존성에서 빠져 있다.** `play-services-ads` 를 넣는 순간 매니페스트 병합으로
  `INTERNET` / `ACCESS_NETWORK_STATE` / `AD_ID` 가 자동 추가되는데, 이는 "네트워크 호출 없음"
  이라는 개인정보 약속과 알림 접근 심사 서사를 직접 훼손한다.
- 켜려면: ① `app/build.gradle.kts` 의 `play-services-ads` 주석 해제 ② `ADS_ENABLED=true`
  ③ 개인정보처리방침·데이터 안전성 섹션 갱신.

검증된 사실 — 병합 매니페스트에 선언된 권한이 **하나도 없다**(androidx 내부용 제외).
ML Kit 이 붙이는 `INTERNET` 도 `tools:node="remove"` 로 뺐고, 그 상태에서 OCR 이
도는 것을 에뮬레이터에서 확인했다.

### 1.5 시각 필수 규칙 완화

PRD §9 는 "추출 필수값은 금액, 상태, 시각, 발신 식별자다. 하나라도 없으면 자동 반영하지 않는다"
고 못박았다. 그런데 **현대카드 문구에는 날짜·시각이 아예 없다.** 규칙을 그대로 지키면
그 카드사 거래가 전부 확인 필요로 쌓여 앱이 무용지물이 된다.

결제 통지는 결제 직후에 도착하므로 수신 시각이 충분히 좋은 근사값이다. 시각을 못 읽으면
수신 시각으로 채우되 `occurredAtEstimated` 를 세워 두고, 거래 상세에
"알림에 거래 시각이 없어 수신 시각으로 표시합니다" 라고 밝힌다. 신뢰도도 0.20 대신 0.12만 준다.

### 1.6 이미지 OCR 로 과거 내역 불러오기

`READ_SMS` 로 문자함을 훑는 대신, 카드사 앱·문자·카카오톡 **캡처 이미지**를 읽는다.
사진 선택기(Photo Picker)를 쓰므로 저장소 권한도 필요 없다 — 사용자가 고른 한 장만 넘어온다.

ML Kit 한국어 OCR 은 모델이 APK 에 통째로 들어 있어(약 39MB) 오프라인으로 돈다.
그런데 매니페스트 병합으로 `INTERNET` / `ACCESS_NETWORK_STATE` 가 자동 추가되므로
`tools:node="remove"` 로 도로 뺐다. **에뮬레이터에서 권한 없이 OCR 이 도는 것을 확인했다.**

대가는 APK 크기다: 11.8MB → **50.9MB**(릴리스). 대부분이 OCR 모델이다.

#### 캡처 화면은 두 종류다

| 종류 | 예 | 파서 |
|---|---|---|
| 통지 한 건 | 카카오 알림톡, 푸시 | `OcrText.blocks` → `PaymentParser` |
| 이용내역 목록 | 우리WON피드, 실적 내역 조회 | `LedgerScreenParser` |

목록 화면은 통지 파서로 못 읽는다. 한 화면에 수십 건이고, 날짜가 구역 헤더에만 있으며,
헤더에 그 날의 **합계 금액**이 붙어 있다(`9월 7일 월요일  142,620원`). 합계를 거래로 읽으면
하루치가 통째로 이중 집계된다. 화면마다 순서도 다르다(우리는 날짜가 앞, 실적내역은 뒤).

#### `Text.getText()` 를 쓰면 안 된다 — 실기기에서 확인

ML Kit 평문 출력은 **화면의 시각적 행 구조를 보존하지 않는다.** 2단 레이아웃에서
오른쪽 열이 통째로 문자열 끝으로 밀린다:

```
개인 구매 추적 한도
1,000,000
한도 저장
…
원          ← 오른쪽 열이
매월 1일     ← 전부 맨 끝에
허용됨
```

카드사 이용내역이 정확히 이 구조라(왼쪽 가맹점 / 오른쪽 금액), 평문을 쓰면 짝이 어긋나
`너른마당 85,000원` 이 사라지고 `푸른들컨트리클럽` 이 두 번 나오는 식이 된다. 실제로 그랬다.

그래서 줄마다 딸려 오는 좌표로 같은 시각적 행을 다시 묶는다(`OcrLayout.rebuildRows`).

#### 은행 거래와 해외 사용

- **은행 거래 제외**: 은행 앱 캡처에 섞인 환전·송금·이체·예금은 카드 결제가 아니다.
  걸러 내지 않으면 카드 실적이 계좌 이체액만큼 부풀어 오른다.
  단 `체크카드출금` 은 카드 결제라 되살린다.
- **해외 사용 분리**: USD 같은 외화 건은 통화별로 따로 세어 홈에 별도 줄로 보여 준다.
  **원화 합계에 넣지 않는다** — 네트워크가 없어 환율을 모르고, 임의 환율로 더하면
  한도·실적 숫자가 거짓이 된다.
- **엉뚱한 캡처 방어**: 카드사 이름을 못 찾은 이미지는 받지 않는다. 앱 설정 화면을 넣었더니
  한도 입력칸의 `1,000,000원` 을 결제로 읽어 100만원짜리 거래가 만들어진 적이 있다.

### 1.7 AI 인식은 쓰지 않기로 했다 (2026-09-08)

OCR 오인식이 잦아 "인터넷 AI 를 쓰면 안 되나" 는 물음이 나왔다. 셋을 검토하고 **전부 보류**했다.

| 안 | 판단 |
|---|---|
| ML Kit GenAI Prompt API (온디바이스 Gemini Nano) | 방향은 맞지만 **기기가 아직 지원하지 않는다** |
| Firebase AI Logic (서버측 키 + App Check) | 키는 안전하나 `INTERNET` 권한이 생겨 §1.4 의 약속이 깨진다 |
| 사용자가 Gemini 키 직접 입력 | 위와 같고, 키 발급 부담을 사용자에게 떠넘긴다 |

온디바이스 안이 유일하게 권한 약속과 양립하는데, 실기기 확인 결과 쓸 수 없었다.
`com.google.mlkit:genai-prompt:1.0.0-beta4` 를 붙여 갤럭시 S24+(SM-S926N, Android 16)에서
`Generation.getClient().checkStatus()` 를 불렀더니 **`0 = UNAVAILABLE`** 이 나왔다
(상수는 `genai-common-1.0.0-beta4.aar` 를 `javap` 로 열어 확인). AICore 는 구글·삼성 것이
둘 다 깔려 있지만 ML Kit GenAI 의 기기 허용 목록에 아직 없다.

의존성과 탐침 코드는 제거했고, 근거는 `app/build.gradle.kts` 주석에 남겨 뒀다.
**지원 기기가 늘면 다시 확인할 것.** 그때까지는 규칙 기반 파서를 계속 다듬는다.

### 1.8 과거 내역은 OCR 이 아니라 **개시 잔액 입력**으로 (2026-09-08 결정 · 2026-09-10 구현)

PRD 는 과거 내역 확보를 `READ_SMS` 재스캔으로 잡았고, 우리는 그것을 캡처 OCR 로 대체했다.
그런데 §1.6 에 적은 실패들을 다 겪고 나서 **방향 자체를 바꾸기로 했다.**

> **이 앱은 명세서 앱이 아니다.** 개별 거래를 정확히 재현하는 게 목적이 아니라
> 그날까지의 총계를 아는 게 목적이다.

그러면 카드앱이 이미 계산해 둔 **"이번 달 이용금액"** 숫자를 사용자가 그대로 옮겨 적고,
그 뒤로 오는 결제 통지를 거기에 더하면 된다. 과거 내역을 한 건씩 복원할 이유가 없어진다.

```
카드 총액 = 개시 잔액(사용자 입력) + Σ(기준 시각 이후 도착한 결제 통지)
```

OCR 로 얻으려던 것을 입력 한 번으로 얻으면서, §1.6 의 특수 처리(글자 오인식·2단 레이아웃·
화면별 구조·은행 거래 혼입)가 통째로 필요 없어진다. **덤으로 총계가 어긋났을 때
사용자가 카드앱 숫자를 다시 넣어 즉시 복구할 수 있다** — 이게 OCR 에는 없던 성질이다.

가장 위험한 지점은 **주기 전환**이다. 개시 잔액은 입력한 그 주기에만 유효해야 하고,
주기가 넘어가면 0으로 봐야 한다. 안 그러면 지난달 사용액이 이번 달에 계속 얹히는데
숫자가 그럴듯하게 크기만 해서 사용자가 알아채기 어렵다.

구현 규칙·화면은 `CLAUDE.md` §4 에 있다. **OCR 코드는 당장 지우지 않는다** —
개시 잔액을 실제로 한 주기 써 보기 전에는 OCR 이 정말 불필요한지 확정할 수 없다.

구현하면서 예상 못 한 함정을 하나 밟았다. 주기 전환은 **읽을 때만이 아니라 쓸 때도**
문제였다. 기준 시각 갱신을 "금액이 지난번과 달라졌는가"로 판단했더니, 10월에 카드앱을
보고 9월과 **같은 금액**을 옮겨 적으면 기준 시각이 9월에 머물러 입력값이 통째로 0으로
읽혔다. 하필 이 설계의 가장 큰 장점("어긋나면 다시 넣어 복구한다")이 막히는 지점이다.
지금은 "기존 기준 시각이 이번 주기 안에 있는가"로 판단한다 — `domain/InitialAmountPolicy`.

### 1.9 기타

- `minSdk` 24 → **26**. `java.time` 과 Keystore AES-GCM 을 디슈거링 없이 쓰기 위함.

## 2. 구조

```
data/
  model/Models.kt        엔티티 + 열거형 (Room 애너테이션 포함)
  db/                    DAO · AppDatabase · TypeConverter
  crypto/DbPassphrase    Keystore 로 봉인한 SQLCipher 암호
  DulSsenRepository      유일한 저장소. 네트워크 경로 없음
domain/
  Cycle                  주기 계산 (Asia/Seoul 고정, 시작일 1~28)
  Aggregator             집계 규칙. 파생 계산만 하고 캐시 없음
  Money / Times          표기
ingest/
  IssuerRegistry         카드사 판정표 (패키지 · 본문 키워드)
  PaymentParser          SMS/푸시/알림톡 공통 파서
  Fingerprint            지문 + 가맹점 표기 비교
  Ingestor               분류·중복 판정 (순수 함수, 기기 없이 테스트 가능)
  SourceGate             알림 접근 상태 조회, 기본 문자 앱 식별
notification/PaymentNotificationListener  유일한 수집 경로. 허용 목록 방식
ui/                      Compose 화면 7종 + 디자인 토큰
```

### 암호화

1. 최초 실행 때 32바이트 난수를 만든다 (SQLCipher 암호).
2. Android Keystore 의 AES-256-GCM 키로 봉인한다.
3. 봉인된 결과만 SharedPreferences 에 Base64 로 남긴다.

디스크 어디에도 평문 암호가 없다. 기기 초기화·앱 삭제로 Keystore 키가 사라지면 DB 는
영구히 열리지 않는다 (PRD §10 "복구 불가" 고지와 일치).

### 백업은 왜 다른 키를 쓰는가

내보내기 파일은 위 DB 암호로 잠그지 않는다. **Keystore 키는 기기 밖으로 나갈 수 없어서**,
그걸로 잠그면 기기를 바꾸는 순간 백업이 벽돌이 되기 때문이다. 그래서 사용자가 기억하는
비밀번호에서 PBKDF2-HMAC-SHA256(210k)으로 키를 뽑아 AES-256-GCM 으로 봉인한다
(`data/crypto/BackupCrypto`). 파일은 내부 저장소에만 두고 공유 시트로 넘긴다.

> 처음 구현은 `"암호화 내보내기"` 라는 이름과 화면 문구를 달고 **평문 JSON 을 외부
> 저장소에** 쓰고 있었다. SQLCipher 와 Keystore 로 쌓아 올린 방어가 그 한 줄로 통째로
> 우회됐다. 2026-09-10 에 고쳤다.

특히 확인해 둘 것:
- `IngestorTest` — 같은 결제가 문자·푸시·알림톡으로 와도 **한 번만** 집계되는지
- `PaymentParserTest` — 누적 실적 금액을 결제 금액으로 오독하지 않는지,
  `롯데백화점`·`하나로마트`처럼 카드사 이름이 들어간 가맹점을 살리는지,
  `(주)한빛상사` 의 `(주)` 가 살아남는지

### 실제 문구 코퍼스

`RealCorpusTest` 는 **지어낸 문구가 아니라 실제 카드사가 보낸 통지**로만 채워져 있다.
출처는 둘이다:

- 사용자 기기에서 직접 채집한 카카오 알림톡 (우리·삼성) → `PaymentParserTest`
- 공개된 파서 프로젝트의 테스트 코퍼스 8개 카드사분
  ([kakao/credit-card-sms-parser](https://github.com/kakao/credit-card-sms-parser), deprecated).
  문구는 카드사가 만든 정형 템플릿이고, 파싱 로직은 전부 새로 썼다.

이 코퍼스를 붙이면서 드러난 것 — **카드사 문구는 생각보다 훨씬 제각각이다.**
아래는 전부 실제로 깨졌던 케이스이고, 지금은 회귀 테스트로 잠겨 있다:

| 실제 형식 | 무엇이 깨졌나 | 어떻게 고쳤나 |
|---|---|---|
| 현대카드 — 날짜·시각이 아예 없음 | 시각 필수 규칙에 걸려 전부 확인 필요로 쌓임 | 수신 시각으로 근사하고 추정 플래그를 남김 |
| 삼성법인 — '승인' 같은 방향어가 없음 | 결제로 인식되지 않고 통째로 버려짐 | 카드사·금액·시각이 다 있으면 승인으로 추정 |
| KB 체크카드출금 — '승인'도 '원'도 없음 | 위와 같음 + 금액 0원 | `카드출금`을 승인 신호로, 단위 없는 금액도 인식 |
| 농협BC — 카드사 이름이 둘 겹침 | 농협(2)·BC(2) 동점이라 판정 포기 | 길이가 같으면 **먼저 나온 쪽** |
| `KB*카드 … 우리사랑동물병원 취소` | 가맹점의 '우리'가 카드사 판정을 이김 | 위와 같음 (위치가 곧 신뢰도) |
| `KEB하나 … 롯데쇼핑(` | 가맹점의 '롯데'를 카드사로 보고 지워 버림 | **감지된 카드사**의 키워드만 지움 |
| `(주)한빛상사` | 앞 괄호만 벗겨져 `주)…` 로 망가짐 | 짝이 맞을 때만 괄호를 벗김 |
| 알림톡 하단 마케팅 문구 | 가맹점보다 길어서 가맹점 자리를 차지 | 길이 대신 **시각 다음 줄**을 우선 |
| 한 줄로 뭉쳐 오는 푸시 | 줄 단위 소거법이 통째로 실패 | 줄이 아니라 조각을 지우는 폴백 추가 |

새 카드사 문구를 만나면 **여기에 케이스를 먼저 추가하고** 파서를 고친다.

카드사 문구 형식이 바뀌면 **테스트에 케이스를 먼저 추가하고** 파서를 고친다.
`PaymentParser.VERSION` 을 올리면 거래에 기록돼 어느 버전이 만든 거래인지 추적된다.

## 5. 심사 주의

Google Play 는 SMS 권한을 민감 권한으로 분류하고 'SMS 기반 자금 관리'를 예외 사용 사례로
열거하지만, 핵심 기능성·다른 방법 부재·권한 선언·검토 승인을 요구한다.
([정책](https://support.google.com/googleplay/android-developer/answer/10208820?hl=ko))

**그래서 이 앱은 SMS 권한을 쓰지 않는다.** SMS 예외 사용 사례는 "다른 방법이 없을 것"을
요구하는데, 알림 접근으로 같은 목적을 달성할 수 있으므로 그 근거가 성립하지 않는다.
알림 접근만 선언해 해당 심사를 통째로 피하고, 결제 문자는 문자 앱 알림에서 읽는다.

대신 알림 접근 자체에 대해 심사 자료를 준비해야 한다:

- 핵심 기능성 — 결제 통지 수집이 앱의 존재 이유이고 다른 방법이 없음
- 허용 목록 방식 — 사용자가 켠 앱의 알림만 읽고, 나머지는 본문을 꺼내지도 않음
- 미전송 — 네트워크 권한 자체가 없어 어떤 데이터도 외부로 나갈 수 없음
- 최소 보관 — 알림 본문은 저장하지 않고, 파싱 결과만 암호화 DB 에 남김

SMS 권한 기반 수집을 되살려야 한다면 이전 커밋의 `sms/SmsReceiver` 를 복원하면 된다.
파이프라인이 소스 중립이라 나머지는 그대로 동작한다.
